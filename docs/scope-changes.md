# Scope changes

Requests that add work beyond proposal §6 follow this process:

1. Ask the client first and get the answer in writing, such as a message, email, or
   meeting notes the client confirms. Do not treat a request as approved without this
   evidence.
2. Add a **Scope change** section to the issue recording who asked or agreed and when,
   which persona benefits and what problem the change solves, and a link to the client's
   written answer.
3. State what the change replaces by naming the story it pushes down or out. If nothing
   moves, explain why the team still has capacity.
4. Once the written evidence and replacement decision are recorded, add one row for the
   story to the approved scope change log below.

## Notes

The proposal for this application was written as a statement of intent rather than a complete specification, and it was never meant to list every feature the final system would contain. Student exchange is a domain with many moving parts: each partner university has its own admission rules, nomination procedures, document requirements, and application timelines, and Kuwait University’s own office handles outbound and inbound students differently. A proposal written at the start of the semester couldn't capture all these variations, because many only became visible once we began working with the client and examined how real applications flow between institutions. The proposal therefore defined the core scope (the application form, automated eligibility screening, the coordinator dashboard, status updates, and the partner nomination portal) and left room for the surrounding features to be shaped as development progressed. As a result, our backlog extends beyond the proposal’s original outline in places, and we later set aside some stories that looked relevant early on as out of scope. This is a deliberate consequence of building the application in close collaboration with the client, with requirements refined through regular feedback rather than fixed in advance, which is an accepted practice in real-world software projects, particularly those following agile methods, where clients often cannot fully articulate what they need until they see a working system.
